# Meal Menu

WordPress-плагин «Календарь питания», PHP 8.0+, WordPress 6.3+. Рабочая документация: `README.md` и `docs/workflow-logic.md`.

## Структура

- `meal-menu.php` — точка входа, константы версии, автозагрузка `Meal_Menu\`, публикация XLSX.
- `includes/class-db.php` — доступ к таблицам `{$wpdb->prefix}meal_*`, календарям и шаблонам.
- `includes/class-shortcodes.php`, `templates/public/`, `assets/js/public.js` — публичный календарь и меню дня.
- `includes/class-admin.php`, `includes/class-ajax.php`, `includes/ajax/`, `templates/admin/` — административные страницы и обработчики.
- `includes/class-excel-*.php` — генераторы daily/TM/KP/OC; `includes/class-importer*.php` — импорт.
- `blocks/meal-calendar/src/` — исходники Gutenberg-блока; `blocks/meal-calendar/build/` — результат `npm run build`.
- `vendor/` хранится в репозитории, чтобы плагин можно было установить без Composer на сервере.

## Правила данных

- `merged_with` объединяет только расписание: даты, номера дней, отметки выходных и признаки цикла. Сохранять общий календарь нужно у его источника.
- Меню каждого отделения использует его собственный шаблон с тем же `day_number`. Не подставлять шаблоны и блюда источника, если локальный шаблон отсутствует.
- Публичное меню и ежедневный XLSX должны выбирать одно и то же отделение. TM относится к собственным шаблонам отделения, KP — к общему расписанию.
- Лагерные таблицы и шаблоны отдельные; не применять к ним объединение школьных календарей.
- При изменении выбора меню проверять чтение календаря, сохранение, импорт, публичный HTML/AJAX и Excel. Ранее опубликованные XLSX требуют повторной генерации после обновления кода.

## Изменения и проверки

- Сохранять стиль существующего PHP-кода, проверки прав и nonce в административных обработчиках, экранирование публичного вывода.
- Проверять синтаксис каждого изменённого PHP-файла: `php -l path/to/file.php`.
- Регрессия объединённых календарей: `php tests/run.php`. Тесты используют изолированные фикстуры и заглушки WordPress; сервер WordPress и рабочая база не нужны. Нужны PHP CLI, зависимости из `vendor/` и расширения, требуемые PhpSpreadsheet.
- При изменении исходников блока выполнить `npm run build` и включить соответствующий результат сборки.
- Не менять вручную `vendor/`, сгенерированные сборки и XLSX. Обновлять их только профильным инструментом при необходимости задачи.
- `reference/` — локальные исходные образцы для сверки. Не изменять, не коммитить и не включать их в релизные архивы. Не добавлять секреты и рабочие выгрузки.
- При изменении поведения обновлять пользовательскую документацию. Версия в заголовке плагина и `MEAL_MENU_VERSION` должна совпадать.
- Коммит и push не означают разрешение на обновление рабочего сайта, изменение его базы или публикацию файлов на нём: для этих действий нужна отдельная просьба пользователя.
